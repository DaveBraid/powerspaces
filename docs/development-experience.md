# 开发经验

只维护影响后续开发的重要、可复用结论，不记录过程流水账或未经验证的猜测。

## 原生玻璃

- `NSGlassEffectView` 应通过 `contentView` 承载前景。把玻璃当作独立背景层会绕开系统对内容的自适应处理；移动层级时必须复核图标悬停溢出、拖放和空白区菜单。
- `alphaValue` 淡化整个合成结果，边缘高光与前景也会受影响。需要保留光学轮廓时，使用原生材质与 `tintColor` 调节染色，并在界面中准确区分“着色强度”和“不透明度”。
- `.regular` 和 `.clear` 都是原生玻璃；前者强调内容可读性，后者更通透。不要把 `.regular` 称为普通模糊，也不要未经对照断言系统 Dock 的私有实现。
- 本机 macOS 27 SDK 没有公开透光率参数，但实测内部 `glassBackground` 的 `inputBlurRadius` 与 `inputFaceOpacity` 可独立减弱背景模糊和底色；保持折射和整层 alpha 原值；原生高光宽度与强度保持不变。私有实现集中于 `GlassBackgroundTuning.swift`，限定系统大版本、探测键与数值类型、复制滤镜再修改；记录系统原值避免滑块反复调整造成累积衰减。
- **高光根因修正（macOS 27.0 / 26A428）**：不能把背景滤镜 `inputKeyFillHighlightHeight`／`Amount` 的可写性当成原生 Dock 上下高光的因果证据。同一 clear 玻璃窗口的实机激活／失活对照显示：独立 `CASDFKeyFillHighlightEffect` 所在 `CASDFLayer.opacity` 从 1 变为 0，`keyColor`／`fillColor` 的 alpha 同时从 1 变为 0；视觉上上下高光随之消失。PS 使用 `.nonactivatingPanel`，仅调背景滤镜无法解决前景高光失活。正式实现已切换到 `.dock` 配方与渲染环境覆盖，保留非抢焦点行为。
- 系统 Dock 的静态构造链已核对：`ModernFloorLayer` → `GlassMaterialProvider.Configuration.dock` → `DLMaterialLayerController`，与公开 `.clear` 配方不同；渲染器支持独立 SDF 玻璃高光。二进制也有 legacy／其他组件的 rim 控制器，不能把所有 rim 符号都归到现代底栏。尚未读取系统 Dock 实时图层，不能声称掌握其完整光效参数。
- AppKit 会重建内部滤镜。通过布局后合并更新及滤镜变化观察重新应用，不能以持续轮询保活；0% 恢复当前系统原值，未知实现不写入。开发验收既要检查参数，也要固定背景做视觉对照。
- macOS 27 的 `effectIsInteractive` 控制交互响应，不是折射开关。单块玻璃不需要为了“效果齐全”而添加 `NSGlassEffectContainerView`。
- 光学验收应固定背景、尺寸、缩放与强度，观察高反差边界形变，再验证非激活窗口、悬停和四向停靠。编译成功与 API 可用均不能代替视觉验收。
- AppKit 的 `NSView.hitTest` 接受父视图坐标。跨容器转发时不要重复转换到子视图局部坐标；同时验证图标内与图标外的命中结果。
- 降低透明度时切换为不透明背景，前景必须继续显示；玻璃与纯色切换时要解除并恢复 `contentView` 归属，不能只隐藏整个玻璃视图。

## 构建与本地化

- 本机 Swift 6.4 默认 swiftbuild 后端曾把 SDK 标记写成部署版本 14.0，使控件回退旧外观。当前使用 native 后端；升级工具链后检查 `LC_BUILD_VERSION` 再移除兼容，不要修改二进制伪造 SDK。
- native 与 swiftbuild 的语言资源目录大小写不同；本地化查找兼容 `zh-Hans` 和 `zh-hans`，必须验证打包后的应用。
- 本机 CLT 未提供 SwiftUIMacros 插件，使用 `ViewState` 别名明确选择原有属性包装器。

依据：[Apple AppKit 接入说明](https://developer.apple.com/videos/play/wwdc2025/310/)、[Apple Liquid Glass 材质说明](https://developer.apple.com/videos/play/wwdc2025/219/)，以及本机 SDK 头文件。

## 应用生命周期

- 程序坞与状态栏的退出菜单共用 `ApplicationActions`，先结束菜单跟踪，再在主队列调用 `NSApp.terminate`。系统 Dock 和快捷键的恢复集中保留在 `applicationWillTerminate`，不要复制清理代码或使用强制结束代替正常退出。
- 原生菜单跟踪期间，冻结宿主 Dock 的列表重建、位置调整和自动隐藏，避免后台刷新拆掉菜单锚点，造成“点击无效”。菜单关闭后恢复正常刷新。

### 程序坞分区与无窗口归属

- 固定项的运行状态来自全局进程表，当前桌面的窗口列表单独维护，避免把其他桌面正在运行的固定项误画成未启动。
- 无窗口进程没有系统 Space 归属；按窗口编号记录桌面 UUID 归属并按进程启动身份持久化，退出清理；首次无历史的无窗口进程归入活动桌面。不能声称这是系统提供的精确归属。同一窗口移动要替换旧归属，不能累计“访问过的桌面”；关闭才保留最后归属。短暂快照缺失保留窗口编号，重新出现仍可修正；最多保留 256 个已关闭窗口编号，较旧记录压缩为桌面集合。候选列表必须包含已归属的所有存活进程，不能用“全局无窗口”过滤，否则其他桌面有窗口时会丢失本桌面图标；多进程应用按窗口 PID 记录归属、按应用键去重显示。
- `NSButtonCell` 的默认图文分配会受图片尺寸影响；明确实现 `imageRect` / `titleRect`，并按实际文本宽度分配按钮空间。图标缩放使用鼠标事件，距离基准固定在一次悬停开始时，避免扩容后重新取中心造成反馈抖动。
- 动态扩容必须同时更新窗口、玻璃和原生 contentView。实机曾测到外层宽 694 点、前景仅 629 点，造成右侧标题裁切；仅加宽按钮无法修复。
- 缩放时不能用变化中的玻璃中心定位图标组；应固定外侧边缘约束，圆点使用独立几何图形并按实际图标中心定位。四边停靠的实测应分别比较屏幕 y / x 坐标，避免字体字形基线造成假对齐。

### 原生 Dock 配方的正式接入（26A428）

- 独立原型及失活日志证实 `DesignLibrary.GlassMaterialProvider.Configuration.dock` 可通过 SwiftUI Material 渲染；关键是私有 `EnvironmentValues.windowAppearsActive = true`。普通 `appearsActive`、`materialActiveAppearance(.active)` 不等价；不得用激活 PS 或伪造 keyWindow 来补偿。
- `NativeDockMaterial.swift` 只托管背景。Swift 私有调用隔离在 `CDockMaterial`，使用 Clang 的 `swiftcall`、`swift_indirect_result`、`swift_context` 标注真实调用约定；所有函数动态解析，不静态绑定私有 setter。参见 [Clang 调用约定说明](https://clang.llvm.org/docs/AttributeReference.html#swiftcall)。初始化器消费输入值，释放原始存储时不能再次析构。
- 只启用 Apple Silicon / macOS 27.0 构建 `26A428`，同时检查完整元数据、Configuration 216 字节、Provider 328 字节、Material 17 字节／stride 24、EnvironmentValues 16 字节及 8 字节对齐、MaterialProvider 见证表、环境 false/true 回读。系统升级后先重新验证，不能只扩大版本条件。
- 渲染后再核对真实 `CASDFKeyFillHighlightEffect` 的图层 opacity、颜色 alpha 和背景滤镜，最多三次延后验证；失败则永久回退该视图的公开玻璃。背景滤镜和渲染树通过观察与布局事件维护，高光仅做只读验证，无持续轮询。
- 正式桥接实测：应用后台／非 key 窗口、480→580 点宽度、浅→深色后高光保持；透光率 0／40／80／100% 及恢复原值通过；原生高光强度和宽度不变、AppKit 命中、纯色切换与公开材质回退通过。此结论不等于取得系统 Dock 的完整实时参数。

- 从 `NSGlassEffectView.contentView` 迁回普通 AppKit 容器时，恢复 `translatesAutoresizingMaskIntoConstraints` 和尺寸管理；原生容器会改变布局模式，仅设置 frame 会导致前景偏移。用同尺寸双材质实机对照及容器 bounds 检查验证。

- 整体黑白适配使用经本机验证的 `CABackdropLayer.tracksLuma`：`captureOnly` 不绘制背景，通过 `backdropLayer:didChangeLuma:`（Double）获得区域平均亮度，0.43／0.57 迟滞阈值避免抖动；不截图或增加应用侧轮询。探测失败或受保护背景回退外观黑白色。逐像素 `vibrantColorMatrix` 会导致同一文字或线条内部混色，不能用于整体选色。采样层必须在文字／标记层下方作为兄弟层，避免采到元素自身，尤其是细线。分割线独立约束到玻璃中心，避免继承图标沿屏幕边缘的对齐。

- `NSTextField` 默认 alignmentRectInsets 左右各 2 点；几何标记继承它并使用自动布局后，1.5 点宽度约束会产生 5.5 点绘制宽度。标记覆盖为零边距，验证实际屏幕矩形的宽度／高度，不能只检查约束常数与中心。

- 桌面归属修复的实机验证：独立普通应用关闭唯一窗口后仍显示在未固定区；保持该进程存活并重启 PS，图标和保存的归属均恢复。跨桌面累计、多进程去重、PID 复用及退出清理另由假数据测试覆盖。首次升级无法恢复未曾保存的历史归属。

- 移窗隔离修复实机：独立测试窗口在两块显示器的不同 Space 间移动，保持同一窗口编号，归属从 A 替换为 B，A 的图标消失；随后关闭窗口仍仅保留 B。隐藏桌面 UUID 来自完整 Spaces 列表，避免只有访问目标桌面后才更新；同显示器移窗路径以假数据覆盖，未操作用户窗口做实测。

- 缩放算法采用用户验证的 `/tmp/ps-dock-magnification-study/Preview.swift`：三倍基础尺寸影响半径、正弦映射左右边界、余弦进出以及 `floor(42 * log(尺寸差 / 2 + 1) + 1)` 毫秒时长。正式版纯函数在 `DockMagnification.swift`，不依赖临时原型文件，也不调用系统 Dock 的私有动画入口。所有几何使用一次悬停开始时的屏幕坐标，图标与间隙同步映射；禁用叠加隐式动画。待处理输入与进出过渡由同一显示链接驱动，稳态暂停回调，拖拽／重建／隐藏先复位；自动隐藏命中区使用变形后的实际窗口位置。

- 玻璃固定厚度后，放大图标会超出材质边界。实测 AppKit 图层重建会恢复宿主 `clipsToBounds`／`masksToBounds`，需在 Dock 宿主布局时保持前景不裁切；四向几何测试同时检查裁切标志，另以纯图标预览检查实际上沿。

- 程序坞缩放会改变窗口及 tracking area，快速跨入其他应用时仅依赖 mouseExited 可能遗漏收尾。复用本地／全局鼠标事件监听，在收到窗口外事件时启动余弦退出；即使关闭自动隐藏，开启缩放仍需该监听。仅处理已有缩放，不增加轮询。

### 原生工作区预留实验（27.0 / 26A428）

- `SLSSetDockRectWithOrientation` 可改变服务器保存的 Dock 矩形，但不等于已运行应用刷新工作区：底部预留 79→119 点，新进程的 `NSScreen.visibleFrame` 和测试窗口 zoom 上移 40 点；提前启动的独立 AppKit 进程即使用标准 `NSApplication.run`，仍保持 79 点。重新取得 `NSScreen.screens` 也无效。不要以新进程验证替代已运行应用验证。
- 核对本机系统 Dock 二进制：矩形变化发送 `0x4b1` 广播，载荷为四个 Float（x/y/width/height）加两个 UInt32（reason/orientation），共 24 字节，随后调用上述 setter；原型载荷与顺序并未漏掉这一通知。AppKit 也注册了 `0x4b1`。
- 根因证据：`SLSPostBroadcastNotification`（`CGSPostBroadcastNotification` 的同一入口）只发单向 Mach 消息；返回 0 是发送成功。WindowServer 的 `_CGXPostBroadcastNotification` 对连接资格做检查，普通实验进程未获投递；只重发当前矩形、给同一消息补回复端口后，实测 `transport=0 reply_id=30222 server_result=1000 (0x3e8)`。不可把传输成功当作服务端授权成功，也不能仅按符号存在启用功能。
- 原型与日志保留在 `/tmp/ps-dock-workarea-study/`：`observer.m` / `observer-run.log`（提前启动、标准事件循环）、`external-run.log`（有独立看门狗恢复）、`ack.m` / `ack.log`（实际拒绝码）；临时路径非仓库依赖。回复诊断使用本机构建反汇编核对的私有函数相对地址，只可用于这次实验，不能进入生产代码。
- 所有测试已恢复底部 79 点并由独立进程回读。未验证其他方向、自动隐藏和普通应用；第二屏仅确认未受底部实验影响，不代表支持逐屏预留。当前不接入仅改变服务器、无法同步现有应用的半成品，也不接管原生 Dock 的特权连接；待找到并验证允许 PS 使用的刷新路径后再实现版本探测、恢复和失败回退。正式 PS 无此工作区写入逻辑。

- 后续刷新路径排查（同一构建）：公开显示配置事务提交原有显示器坐标，返回成功但提前运行的 AppKit 观察进程仍保留旧工作区；未改变分辨率／排列，实验后独立回读恢复 79 点。日志为 `noop.log`、`observer-noop.log`。事务作用域参见 [Apple CGConfigureOption](https://developer.apple.com/documentation/coregraphics/cgconfigureoption)，不能靠成功返回判断缓存已刷新。
- `SLSSpaceSetEdgeReservation` 的 WindowServer fallback `_XSpaceSetEdgeReservation` 仅在空间是自身所属平铺管理对象且其类型为 4 时更新预留，否则也返回 0；本机普通桌面只读类型为 0。此入口不是已验证的普通桌面通用预留接口；现代 bridged 路径尚未证明可用于普通桌面，不调用未知参数污染用户空间。
- 系统 Dock 在传统矩形广播后还向 `WindowManager.ExposeCoordinator.setDockInfo` 传递显示器、当前／最大 inset 和方向；该路线经 `AdminXPCConnection.xpcSetDockInfo`，`AdminXPCListener` 在接受连接前检查 `com.apple.private.windowmanager` entitlement。只读反汇编确认该检查，没有尝试伪造签名或取得该权限；不能把此入口当作第三方可用替代通知。

- 通知徽章缓存必须区分读取失败与明确空字符串：失败保留旧值，完整列表成功后才清理消失项；同 bundle 的多个源若冲突则保持未知，禁止按显示名称或窗口数量生成通知数。覆盖层用 NSButtonCell.imageRect 定位，避免标题宽度改变徽章位置；红色通知与蓝灰窗口数上下分离。
- 当前徽章实机验证阻塞于辅助功能授权：命令行原型及原安装路径的 PS 只读诊断均报告 AXIsProcessTrusted=false，AX 读取返回 -25211；已验证缓存和静态徽章布局，尚未验证系统 Dock AXStatusLabel 的实际内容、变化通知、隐藏／重启和应用退出。启用并确认授权后必须继续实测，不能把静态预览当成来源验证。


### 本地更新与辅助功能签名身份

- 临时签名的 designated requirement 是 `cdhash`，内容变化会改变身份；保持 bundle ID／路径无法独自解决旧授权失效。
- 固定自签名证书产生“bundle ID + certificate leaf SHA-1”要求，不依赖构建哈希；密钥放在仓库外的独立钥匙串，权限限制为当前用户，不添加系统证书信任。签名配置存在而不可用时必须停止，不能悄悄回退。
- 依据：[Apple TN2206](https://developer.apple.com/library/archive/technotes/tn2206/)。首次身份迁移需用户重新授权；相同签名要求的验证不能替代真实 TCC 跨版本测试。


### 图标居中与运行标记

- 程序坞厚度变化时，静止内容外沿应为（玻璃厚度－静止内容厚度）／2，不能固定为圆点留白；内容建立、标题宽度变化后必须同时刷新厚度和定位约束。
- 左右停靠时图标与展开标题作为整体居中；通过平移对齐框处理不同宽度，运行圆点反向补偿该位移以保持公共基线。放大仍使用静止外沿，不能用放大后的尺寸重新计算静止中心。


### 缩放伪退出与事件坐标

- 对照独立实验的前后日志，确认修复前存在鼠标仍在窗口内却请求退出的输入，修复后该现象消失；这会使缩放目标在 1／0 之间来回切换。
- `inVisibleRect` 自动更新追踪区域；容器和按钮均保留同一 tracking area，不在每次缩放布局时重建。实时输入直接读取屏幕鼠标坐标，避免旧事件局部坐标加上新窗口原点。
- mouseExited／事件发给其他窗口只触发退出核验。矩形内还须用公开 `NSWindow.windowNumber(at:belowWindowWithWindowNumber:)` 核对最上层可点击窗口，避免遮挡后的悬停残留；窗口遮挡通知补充鼠标静止时的复核，无 AX 或持续轮询。
- 四向真实窗口检查覆盖伪退出、同屏幕点焦点稳定、追踪区域复用及高层非激活窗口遮挡；遮挡测试须等待 WindowServer 提交，并先恢复缩放目标以排除通知已提前收尾的假阳性。保留原有菜单、拖拽与隐藏状态保护及正弦／余弦算法。


### 高频输入与显示刷新

- 鼠标回调直接布局会把高频设备输入、重复追踪事件和动画计时器叠加为无效重绘；改用所在视图的公开 CADisplayLink，每帧合并最新屏幕坐标，与余弦过渡共用一次布局。静止 250ms 后暂停并复用链接，退出／拖拽／隐藏时清理；使用弱回调目标避免保留环。
- 相同焦点与进度跳过几何更新，窗口变形不强制同步显示。即时退出取消待提交输入，防止下一帧重新放大。
- 本机双图标独立窗口的 480 次突发输入，原逐事件布局约 177 ms；合并后含一次布局在本轮重复检查中约 1.8–6 ms。此项验证输入积压成本，不能当作真实帧率或端到端延迟；回归同时断言最后位置生效、空闲暂停、待提交输入可取消。


### 缩放期间脱离整条约束布局

- 突发输入耗时不能证明持续绘制流畅；`--check-dock-performance` 使用 12 个真实图标、混合标题和显示链接连续测量。当前 60 Hz 显示器上，原路径单帧同步工作 P95 约 12 ms，新路径约 7.5 ms；显示回调约 150 次／2.5 秒。该数据不代表 GPU 呈现帧率，也不能宣称已验证 120 Hz。
- 缩放时保留原视图和父子关系，只暂时移出 NSStackView 排列、暂停项目尺寸约束，直接应用正弦映射后的屏幕矩形；统一提交布局。项目访问统一读取快照，退出、拖拽、菜单收尾、隐藏和重建时恢复原排列约束。
- 悬停开始一次预留最大变形窗口，逐帧只改内部玻璃和图标，避免 WindowServer 重复调整窗口。透明预留区必须停止截获鼠标，跨应用监听负责重新进入；退出与自动隐藏按可见区域判断，不能按扩大的窗口矩形判断。
- 回归覆盖固定窗口、四向实际图标尺寸、公共圆点基线、徽章与分割线、透明区穿透及重新进入、遮挡、菜单、拖拽和隐藏恢复。模拟隐藏后须走真实 reveal 恢复窗口位置，仅恢复状态枚举会制造假失败。

### 静态悬停预览的会话与权限

- 预览归属复用 `DockModel.apps(onDisplay:)`，截图列表只用于 ID＋PID 关联，不能推断桌面归属。点击通过 Launcher 重新读取归属并走精确聚焦，避免复用 Dock 点击的“前台则最小化”切换语义。
- ScreenCaptureKit 异步取消不保证底层请求立即停止：全局保留一个工作任务，等待它返回后才启动最新待处理会话；令牌和取消检查共同阻止旧截图回写。每次展开一次捕获，不把截图或窗口枚举放进鼠标／动画回调。
- 关闭 NSPanel、清空视图引用不足以保证图片立即释放，AppKit 可能暂留旧视图；回归发现后改为先逐项清空 NSImageView.image，再移除内容。四向布局检查同时验证图片弱引用释放和会话令牌失效。
- 屏幕录制与辅助功能分开授权；预览默认关闭，关闭时不检查或申请捕获权限，只有设置按钮主动发起申请。诊断进程必须使用正式路径和稳定签名，独立原型的授权不代表正式 PS 已授权。
- 本机正式固定签名、通过 LaunchServices 正常启动的 PS 已确认两项权限均可用；从命令行直接执行同一二进制会将 AX 状态报告为 false，不能据此断言正式应用丢失授权。`--check-preview-capture` 仅针对 `local.ps.preview-validation` 独立测试应用：实测一张可见窗口缩略图、一项最小化占位，捕获不激活；最小化恢复、指定窗口置顶及隐藏恢复均通过。真实跨屏鼠标过渡仍需交互验证，不能由几何检查替代。
- 悬停的权限／错误提示不能使用固定文本框高度；先设置 NSPanel 内容尺寸，再安装内容视图；否则从零尺寸扩展时 autoresizing 会把文字挤出上边缘。按当前语言和可用宽度测量换行高度，再在屏幕边界内定位；回归同时检查子视图位于内容边界内。


### 显示刷新节拍不能逐帧暂停

- 侧对话真实鼠标 A/B 日志显示，每处理一帧就暂停 CADisplayLink 会不断重新唤醒；部分时段处理仅约 1–4ms，回调间隔 P95 仍达 180–330ms。持续回调的自动 CPU 基准绕过了此路径，不能据此宣称真实操作流畅。
- 正式输入只负责唤醒；移动期间每帧读取最新 `NSEvent.mouseLocation`，静止 250ms 且过渡结束后才暂停，离开后完成余弦退出并停止。保留遮挡命中和窗口预览跨间隙保护；未采样真实输入的固定几何预览独立处理。未引入实验中的基准位置缓存、图标预栅格化或标题改动。
- 最终实验真实输入记录的主要移动时段回调间隔 P95 约 17–20ms，用户已确认实验手感；这是该实验环境的记录，不能推算其他刷新率或正式版本端到端帧率。正式回归通过同一事件入口和实际 CADisplayLink，注入可控屏幕位置，在四向检查连续采样、最新坐标、静止停表、恢复和退出；此项是调度验证，不冒充真人鼠标体验。


### 全屏分区与运行／窗口状态分离

- 全屏属于 Space 元数据（现有系统类型 4），不能按窗口大小或仅按可见显示器 `isFullscreen` 推断。扫描全部显示器的 `Spaces`，窗口通过 `spaceIDs` 关联；未知类型不猜测。共享项用稳定窗口 ID 标记，先从本桌面窗口列表移除，再尾部追加，避免同一全屏窗口重复出现。
- `pid != nil` 只表示进程运行；本桌面的 `windowCount == 0` 不代表整个应用无窗口。独立保存全局窗口状态，按 bundle ID（缺省 PID）匹配，最小化和隐藏窗口保留；图标单独调暗，不能降低整个按钮透明度导致运行灯、徽章一起变暗。
- 共享全屏项允许用户明确点击后跨桌面聚焦，执行前重新核对窗口 ID、PID、应用标识和全屏 Space。复用精确置顶，不走普通 Dock 点击的最小化切换或无窗口新建路径；关闭窗口仍复用现有操作。元数据丢失或窗口已退出全屏时拒绝过时目标。

- macOS 27 实测：可见窗口的 ScreenCaptureKit 捕获正常，其他 Space 全屏窗口的新旧静态截图接口均返回 `-3811`；取消全局裁剪和偶数尺寸也未解决。旧公开 `CGWindowListCreateImage` 按窗口 ID 能取得离屏内容，因此只在已有屏幕录制权限、系统 27、符号存在且 ScreenCaptureKit 失败时回退；工作线程串行捕获，核对 PID、防窗口 ID 复用，输出缩略图后释放原图。受控测试确认 440×247 图像内容正确，桌面和前台应用保持不变，不以“返回非空图片”代替内容验证。

- 同一受控应用同时有普通窗口和其他 Space 的全屏窗口时，`AXWindows` 只返回普通窗口；仅按 PID 激活或原生 front-process 调用不能证明选中了指定窗口。明确点击时做限时 250ms 的 AX remote-token 补查，必须同时匹配窗口 ID 与 `AXWindow` 根节点，再复用现有精确置顶；当前私有布局仅启用 macOS 27.0 / 26A428，失败提示而不随意聚焦其他窗口。受控实测“离屏、正确内容、截图不改变桌面／前台、点击精确聚焦”四项均通过；未把此补查放进鼠标或常规刷新回调。

### 图标明暗不能直接使用原始窗口快照计数

- 企业微信关闭主窗口后仍保留无 Space 归属、不可见的大尺寸窗口对象；网易邮箱大师还会留下属于另一显示器当前 Space 的离屏对象。原始快照为窗口操作保留的候选对象不能直接表示“有打开窗口”。

### AX 提前接管窗口布局原型：接入前结论（尚未接入 PS）

- 复核 `/tmp/ps-ax-avoidance/Preview.swift`：Option＋绿色按钮、标题栏空白双击、Fn＋Control＋F/R/方向键及窗口菜单共用 `performLayout`，先拦截再直接向避让目标做 300ms 余弦过渡；这属于应用窗口布局接管，不会改变系统工作区。用户已确认多入口手感；安装的实验 App 与 `MultiEntryBuild` 的 `__text` 哈希一致。所给 `multi-entry.log` 仅有 `READY trusted=false` 和权限阻断，不能当作多入口成功日志。
- `button-fixed.log` 记录邮箱大师绿色按钮 `identity=false semantic=true` 后成功调整，证明不能单凭 `CFEqual` 判断按钮；应组合按钮 role/subrole、所属窗口 ID/PID 和命中范围。该日志 8 次结果中有一次还原失败；动画实际约 323–339ms、14–18 帧，单次 AX 写入 P95 约 15–23ms，不能以请求 120fps 宣称实际达到该帧率。
- 事件回调仍执行同步 AX 命中、父链遍历、尺寸及可写性查询；普通单击也会查菜单。命中查询的 50ms 限制不能等同整条回调预算，其他查询和遍历会累积。正式方案应由前台窗口／菜单通知准备有限缓存，回调只处理有明确证据的候选事件，设置整次截止时间；缓存失效或尚未就绪时放行，不为事后纠正补一次缩放。菜单取消成功前不得启动窗口修改，避免系统菜单与 PS 同时布局。
- `animationBusy` 为全局标志，忙时返回 true 会吞掉新命令；当前动画无取消令牌，用户拖动或关窗后仍可能写最终目标。需按窗口建立事务，以 PID＋进程启动身份＋窗口 ID 标识，新命令从当前实测位置接续最新目标；关闭、手动调整、切桌面、权限失效或停用时取消旧写入。动画写入串行、按时间跳过过时帧，减少动态效果仍直接应用目标。
- 原型还原失败也删除快照，显式 restore 未先核对是否已被用户手动修改，退出会排队等待当前动画后再恢复。正式实现仅在窗口身份和最后实际写入矩形仍匹配时恢复；成功确认后才清记录，受最小尺寸等约束失败时保留可解释状态，不反复强制重试。原型 `attach/enqueue/adjust` 未接入启动路径，是遗留的事后调整实验，不应随提前接管方案带入。
- 正式几何输入应来自对应显示器 PS Dock 的静止玻璃区域及距屏幕边缘距离，不能用含放大预留透明区的 NSPanel.frame。将此边界与系统 visibleFrame 求交，避免重复扣除系统 Dock／菜单栏；按显示器 UUID 管理，处理负坐标、上下排列及四向停靠。建议自动隐藏／不显示的 Dock 不预留常驻区域，悬停显隐不推动窗口；该行为需在接入阶段确认体验。
- 菜单标题的中英文对照不足以证明是系统平铺命令：需要核验完整菜单路径、可用状态及可取得的命令标识／快捷键信息，排除同名自定义项、多窗口布局和全屏命令；未知语言或无法确认的项放行。快捷键不能只靠固定键码假定仍是系统绑定；双击必须尊重实际系统设置。
- 接入前补齐各入口与还原的成功／失败记录，并逐项验证：连续不同指令及跨窗口输入、动画中拖动／关窗／退出、菜单取消失败与键鼠释放配对、事件 tap 超时恢复、权限缺失、应用尺寸限制、四向多屏和自动隐藏。绿色按钮悬停布局面板、边缘拖拽平铺、第三方改尺寸继续明确列为未覆盖；不引入全局事后追踪纠正。

### AX 原型复验：授权、识别覆盖与几何重复扣减（2026-09-19）

- 实验 App 反复丢失辅助功能授权，根因不是证书不受信任，而是 `codesign` 未带 `--keychain`：身份不在默认搜索列表时签名静默退化为 ad-hoc，cdhash 随每次重建变化，TCC 授权随之失效。`find-identity` 报 `CSSMERR_TP_NOT_TRUSTED` 属误报，带 `--keychain` 指向 `~/Library/Application Support/Powerspaces/Signing/local.keychain-db` 即可正常签名。指定要求稳定为 `identifier "local.ps.axavoidance.stable" and certificate leaf = H"ede24be8…"`，同一身份重签可跨重建保持授权。`sign-experiment.sh` 固化该流程并拒绝 adhoc 结果。
- 不能用整文件哈希或 CodeDirectory 页哈希判断「只换签名未换代码」：签名嵌入 Mach-O，`codesign` 会把签名槽清零后重算页哈希，ad-hoc 槽与真实身份槽大小不同（832B 对 18912B），填充字节落在首页内，页哈希必然变化。应改用行为判据（入口标识字符串在位、可正常启动并写出 `READY`）。
- 绿色按钮 AX 形态覆盖率（聚焦窗口、`depthLimit=7`）：Safari、Tabbit、腾讯会议均为 `AXButton/AXFullScreenButton`，上溯 1 级到 `AXWindow`，`identity=true semantic=true`，可识别；微信命中为 `AXWindow/AXStandardWindow`，既无 identity 也非 semantic，父链上不存在按钮节点，属明确不可识别。Finder、Obsidian、Ghostty 因被其它窗口遮挡未能判定。系统设置同属可识别形态，但实测命中查询返回了遮挡窗口的元素，说明授权判定必须校验命中元素的 PID 属于目标应用，遮挡即放行。
- 命中查询耗时（`CopyElementAtPosition`，各 100 次）：中位数 0.1–1.5ms，但 Safari p99 达 46.7ms、Code 达 48.9ms，更大样本曾出现 55.9ms 与 61.4ms。50ms 硬预算正好压在 p99 上，约 1% 的查询会被误拒而放行原操作。接入时应放宽到 80–100ms，或允许一次重试，并保持「无法确认即放行」的语义。
- 几何重复扣减已实测确认：主屏 `axVisible` 高 1331pt（系统已扣 109pt），原型 `allowed` 从 frame 底边扣 140pt 后再与 `axVisible` 求交，实际净预留 170pt，多扣 61pt；无 Dock 的副屏无此问题（净预留 140pt）。原型用 `visible.intersection(allowed)` 与既有结论「应与此边界求交，避免重复扣除」自相矛盾，正式实现必须按 Dock 静止玻璃区域相对屏幕物理边的距离计算预留，而不是叠加到 `visibleFrame` 之上。
- 自动化取证的测试框架教训：`NSRunningApplication.activate` 与随即投递的合成点击之间存在竞态，目标应用未真正前置时，点击会落到恰好覆盖该坐标的其它应用窗口上（本次曾命中正在使用的浏览器窗口）。用合成输入做验证时必须在前台状态确认后才投递，并先校验命中元素的 PID；该竞态是测试框架缺陷，不影响真实用户操作路径。

### AX 原型逐项验证结果（2026-09-19 第二轮，尚未接入 PS）

验证方式：以持久身份签名并授权实验 App，用事件 tap 的真实输入路径驱动，几何结果按原型 `performLayout` 规则独立复算后逐字节比对。

- **键盘入口（`Fn＋Control＋F/R/方向键`）通过**：`source=system-key` 成功接管，`fill` 与 `left/right/top` 实测几何与复算期望完全一致（`-0.0` 仅为浮点负零）。`bottom` 返回 `success=false`、`write size=-25204`，原因是目标高度 635pt 低于窗口可设最小值，属系统/应用约束而非缺陷；这类失败已正确记为失败且未强制回写。
- **还原语义通过**：正常 restore 精确回到初始矩形并 `recordRetained=false`；布局后手动改窗再按 restore，得到 `REJECT restore ownership`，窗口保持用户位置不动、记录保留，符合「身份与最后实际矩形匹配才恢复」的门槛要求。
- **连续输入接续通过**：150ms 内连发 `left` 后 `right`，`generation` 由 8 接续到 9，新命令从当前实测位置 `(208,148,1017,806)` 起算，最终几何等于 `right` 期望值——旧原型「忙时吞掉新命令」的问题已消失。
- **自动隐藏模拟通过**：以 AX 勾选「模拟自动隐藏」后，日志 `autoHide=true` 且目标高度为可用区域满高（副屏 1410pt），零常驻预留生效；系统最终给到 1409pt，差 1pt 为窗口尺寸取整。
- **多屏通过**：窗口移至副屏后，日志正确识别 `screen=(2560,0,2560,1440)`（未误用主屏状态），目标按副屏计算。
- **事件 tap 取消路径通过**：日志出现 `CANCEL reason=pointer-down`，指针按下时旧动画被取消，未继续写入。
- **命中查询存在两处真实限制**：① 遮挡时 `AXUIElementCopyElementAtPosition` 返回遮挡窗口的元素（实测为通知中心 `pid 657` 的浮动窗口，以及全屏的腾讯会议窗口），此时必须校验命中元素 PID 是否属于目标应用，不符即放行；② 即便命中正确按钮，仍可能返回 `hitError=-25204`（`kAXErrorCannotComplete`），日志显示 `CALLBACK elapsedMs=63.7`，即 50ms 预算被突破。综合前述 p99 数据，接入时应把预算放宽到 80–100ms 或允许一次重试。
- **窗口菜单入口可读但合成点击未能验证**：AX 可读取「窗口」菜单的完整项表、位置、可用状态与层级，`填充`／`缩放`／`居中`／`移动与调整大小`／`全屏幕平铺` 均在 `AXMenuBarItem(窗口) → AXMenu` 路径下，与原型排除「全屏幕平铺」的规则一致。但合成点击打开菜单后枚举下拉项不稳定，该入口与**标题栏双击**均留待真实手测。
- **`填充` 项可能被禁用**：Safari 窗口铺满屏幕时「填充」为 `禁用`，原型按 `enabled` 过滤后不接管并放行原操作，属正确行为；验证菜单入口需先选一个该项可用的窗口状态。
- 合成输入验证的固有风险：`NSRunningApplication.activate` 与随后投递的点击存在竞态，本环境有应用持续抢焦点。测试框架必须在前台状态确认后才投递并校验命中 PID，否则点击会落到恰好覆盖该坐标的其它窗口上。
- **标题栏双击入口未能取得可信证据**：Finder 上标题栏取点命中为 `AXButton`，被原型按角色规则拒绝（双击确认只接受 `AXWindow`／`AXTitleBar` 角色，且要求控制按钮位于该按钮中点 ±14pt 内）；Safari 上同一次测试命中为 `AXDockItem`，坐标明显有偏差。后者说明合成双击的取点或投递不可靠，因此这两个结果都不能用于判定该入口是否可用，必须真实手测。可复用的结论是：标题栏区域在部分应用报告为 `AXButton` 而非 `AXTitleBar`，双击识别不能只依赖 `AXTitleBar` 角色存在。
### AX 原型缺陷定位：身份标识与写入事务（2026-09-19 第三轮）

用事件 tap 真实输入路径采集，并在 `performLayout` 与菜单上溯路径加埋点后定位到两处实现缺陷，另有两条测试方法学结论。

- **`launchDate` 不能作为窗口身份标识的前置条件**：原型用 `"\(pid):\(launch.timeIntervalSince1970):\(id)"` 标识窗口，但 `NSRunningApplication.launchDate` 对部分进程恒为 `nil`——实测 Finder 全生命周期为 `nil`，Safari 有值。这使 Finder 上绿灯、标题栏双击、窗口菜单三条路全部被同一守卫挡死；即使在 Safari 上，11 次运行中也有 3 次取不到该字段（约 27% 失败率）。身份标识应只用 pid 与窗口 ID。修复后 Finder 上双击立即出现 `INTERCEPT source=title-double-click`。
- **位置与尺寸必须在分开的 AX 写入里分段提交**：日志反复出现 `write size=-25204 position=0`，即位置写入成功、尺寸写入被系统拒绝，动画随即以 `success=false` 中断并把窗口留在中间尺寸（用户观感是「动了但没到位」）。把两者放进同一次快速提交会被拒绝；改为「先位置、间隔约 100ms、再尺寸、再确认位置」并在动画结束时补写一次目标，而不是直接放弃。
- **合成输入与硬件输入的事件坐标在 tap 中不一致，不能互证**：真实鼠标点击送进事件 tap 时 `event.location` 为左上原点坐标（实测点击菜单项得到 `(74,202)`，与 AX 坐标一致，原型据此正确识别）；而 `CGEvent.post` 投递的同一屏幕点在 tap 中读回的是左下原点坐标（实测投递 `(1356,1294)` 对应真实位置 `(1356,146)`）。因此用合成事件复现硬件路径会得出错误结论——早期多次「命中 `AXDockItem`／`AXScrollArea`／`AXZoomButton`」的异常结果均源于此，不能据此判定原型缺陷。凡涉及事件坐标的验证必须以真实输入为准。
- **标题栏空白区在真实应用里极窄，双击识别不能只认 `AXWindow`／`AXTitleBar` 角色**：在 Finder（宽 900pt）与 Safari（宽 2545pt）上逐点扫描交通灯水平线，同一水平线上绝大多数命中为 `AXButton`、`AXStaticText`、`AXRadioButton/AXTabButton`；真正报告为 `AXWindow` 的只剩零散窄缝，最宽处约 12–16pt，Finder 上单段最长约 132pt。用户按直觉双击标题栏时通常命中标签页或工具栏按钮而被拒绝。正式实现应改为「先按几何判定该点位于标题栏带内（窗口顶边与最小化按钮底边之间，且不落在任一交通灯按钮及工具栏控件内）」，再结合命中元素的所属窗口校验，而不是要求命中元素本身是窗口或标题栏角色。
### AX 原型三入口全部跑通：菜单来源判据与两个稳定性缺陷（2026-09-19 第四轮）

本轮把入口③（窗口菜单）从「始终失败」调到「全部命令通过」，并修掉两个间歇性缺陷。最终统计：`fill` 8/8、`left`/`right`/`top`/`bottom`/`topLeft`/`topRight`/`bottomLeft`/`bottomRight` 各 1/1，拦截 16 次、成功 16 次、失败 0、无结果 0；几何逐字节等于按 `performLayout` 规则独立复算的期望值。

- **菜单来源判据：前两种写法均被实测证伪**。①「上溯父链遇到标题为『窗口』的 `AXMenuBarItem`」——Safari 的菜单父链从子菜单直接跳到工具栏分组（`AXGroup → AXButton → AXWindow → AXApplication`），链上根本没有菜单栏项；②「最外层菜单挂在 `AXMenuBar` 之下」——从最外层菜单上溯 24 层也未遇到 `AXMenuBar`。任何依赖菜单栏归属的校验在 Safari 上都不成立。
- **可用的来源判据是成员集合特征**：取最外层 `AXMenu`，其直属子项中必须命中至少两个系统布局命令成员（填充／居中／移动与调整大小／二等分／四等分／排列／全屏幕平铺／恢复上一个大小等），并配合「命中元素 PID 属于目标应用且非自身进程」。同时必须维护排除表：`全屏幕平铺`、`屏幕左侧/右侧`、以及 `左侧与右侧` 一类多窗口排列项一律放行，否则会接管系统原有行为。
- **歧义命令必须按「前一个分组标题」消歧**：Safari 在同一子菜单内用**禁用的**分组标题 `二等分`、`四等分`、`排列` 划分区段，`左侧/右侧/顶部/底部` 与 `左上/左下…` 分别落在前两个区段。不能看父菜单标题（父菜单无标题），要看该标题之前最近的分组标题，否则半屏与四分之一屏会互相混淆。
- **`AXCancel` 只对最内层菜单有效**：对最外层菜单调用返回 `errAECoercionFail(-25204)`，而原型把最外层菜单传给了取消逻辑，导致「菜单取消失败 → 不启动布局」。改为传入上溯遇到的第一个（最内层）菜单后取消成功。
- **菜单关闭会让应用重建窗口的 AX 元素**：实测 Safari 在 `INTERCEPT` 后约 38 ms 报 `window-unavailable`，持有的旧元素失效；即使重新按 pid 解析，仍会遇到「读取返回成功（`posErr=0`）且 subrole 正常、但取不到 position 值」的过渡态。修法是动画开始前重新解析聚焦窗口，并对几何读取做短暂重试。这两处修完后 `window-unavailable` 与读取失败均降为 0。
- **事件 tap 读到的鼠标坐标是左上原点，与 AX 坐标一致**：用 `CGEvent.post` 合成点击时必须按左上原点投递，不要按左下原点翻转。实测同一枚绿灯，翻转投递会偏移到另一个元素（命中 `AXGroup` 并被拒），不翻转则 `identity=true semantic=true` 通过。此前多轮「合成点击命中 `AXDockItem`／`AXScrollArea`／`AXZoomButton`」的异常结论均源于这一个错误，与原型无关。
- **子菜单项必须悬停展开后才出现在 AX 树中**：脚本化验证菜单命令要沿路径逐级 `mouseMoved` 悬停父项，再点击目标项；直接点击父项会关闭菜单而非展开。
### 窗口布局避让接入正式应用（2026-09-19）

原型验证通过后已按用户授权接入 PowerSpaces。实现分两层：`Sources/SpaceKit/WindowLayoutGeometry.swift`（纯几何与身份，可单测）与 `Sources/SpaceKit/WindowLayoutInterceptor.swift`（事件 tap、菜单识别、动画事务）；应用侧接线在 `AppDelegate.applyWindowLayoutInterception()`、`DockPanel.layoutReservation()` 与 `Sources/PowerspacesApp/DockReservationSource.swift`，开关为 `windowLayoutInterception`（**默认关闭**）。

- **预留量必须只扣系统尚未扣除的部分**。系统 `visibleFrame` 已为 macOS 自己的 Dock 与菜单栏留出空间，而 PowerSpaces 的程序坞常停在系统 Dock 所占的同一块区域。原型原本「从屏幕物理边扣 reserve，再与 visibleFrame 求交」，在主屏上因交集取严而使预留完全失效（实测可见区 y=30..1361、程序坞厚 78pt，交集后仍为 1331pt 高）。正确做法是逐边比较 `visibleFrame` 相对物理边已让出的量，只额外扣除 `reserve - 已让出`。主屏实测：程序坞 78pt 已在系统让出的 79pt 内 → 不额外预留；设成 140pt 时恰好多让 61pt，与原型阶段量到「多扣 61pt」的数值吻合。
- **预留在正式实现中改为量程序坞玻璃在屏幕上的实际内沿**。曾先后试过两种错误做法：只取 `barThickness()`（玻璃厚度，实测 78pt）会让窗口底边正好压在程序坞上；只用系统 `visibleFrame` 已让出的量推断，则完全测不出 PowerSpaces 程序坞（它停在系统让出区域之外）。正确做法是取玻璃视图 `effect` 在屏幕坐标下的实际 frame，换算成距对应屏幕边的距离（实测主屏 119pt：物理底边 1440 − 玻璃内沿 1321）。面板窗口比玻璃更高（含悬停放大余量），不能用面板 `frame`。
- **坐标约定的坑复现两次**：`CGEvent.post` 的合成事件在事件 tap 中按左上原点读取（与 AX 一致），不要做左下原点翻转；翻转后同一坐标会落到另一个元素上（绿灯翻转投递会命中 `AXGroup` 并被拒，双击翻转投递会让 `event.location.y` 偏出标题栏带）。真机硬件输入不受影响，只有自动化验证需要遵守。
- 三入口在正式应用内实测通过：Option＋绿灯、标题栏双击、窗口菜单「填充」均产生 `INTERCEPT → RESULT success=true` 并按几何带正确落位。`WindowLayoutDiagnostics`（`/tmp/ps-window-layout.log`）保留为落盘诊断，便于排查「识别到了但没有接管」。

正式接入后的实测值（主屏 2560x1440、程序坞停底部）：玻璃视图 `effect` 在屏幕坐标下为 `(701, 85, 1158, 78)`，即玻璃底边距屏幕底 85pt；系统 `visibleFrame` 底部已让出 35pt，故额外预留 50pt，可用区落到 `(0, 30, 2560, 1325)`，窗口底边距玻璃内沿仍有 16pt 间隙。副屏程序坞玻璃仅距屏幕底 6pt（几乎贴边）。三入口在该配置下实测一致落到同一目标矩形。

**预留量的正确来源（2026-09-19 修正）**：先后试过三种错误做法，最终定为**取程序坞面板自身的布局尺寸**（`DockPanel.panelSize()` 的横轴，实测底部停靠 129pt）：

| 做法 | 结果 |
| --- | --- |
| 只取 `barThickness()` 玻璃厚度（78pt） | 窗口压在程序坞上 |
| 取玻璃视图 `effect` 的屏幕内沿（6pt） | 更糟，等于没预留 |
| 用系统 `visibleFrame` 已让出的量推断 | 官方 Dock 隐藏后系统只留菜单栏，推断不出 PS 程序坞 |
| 读窗口 `frame` 反推 | 定位/动画过程中读回 y=0，与实际占位不符 |
| **取 `panelSize()` 横轴（129pt）** | 窗口底边 1311 = 程序坞顶边 1311，零重叠 |

官方 Dock 隐藏后主屏 `visibleFrame` 只剩菜单栏 30pt，程序坞完全落在系统让出区域之外，因此**必须按 PS 程序坞自己的尺寸预留**，不能再依赖系统几何。另确认：事件 tap 读到的鼠标坐标与投递坐标一致（左上原点），合成输入无需翻转。

### 程序坞预留的最终实现与外部改尺寸纠正（2026-09-20）

**预留量 = 屏幕物理边 → 可见玻璃外沿**，两个输入都必须取对：

- **位置取窗口服务器**：AppKit 的 window `frame` 在定位后与真实占位不符——实测面板读回 `(695, 0, 1170, 129)`（看似贴屏幕底），而窗口服务器 `CGWindowListCopyWindowInfo` 报 `(695, 1311, 1170, 129)`。必须按 `kCGWindowOwnerPID` + `kCGWindowNumber` 从窗口服务器取真实边界。
- **外沿取玻璃偏移，不取面板总高**：面板比玻璃高出一段看不到东西的透明带（实测 129pt 对 78pt），按面板总高预留会让窗口与可见程序坞之间空出约 50pt。玻璃在面板内的偏移由 `effect.convert(effect.bounds, to: nil)` 得到，各边外沿 = 面板对应边 + 玻璃在该侧的偏移。
- 实测结果：玻璃顶边 = 1311 + 6 = 1317，从屏幕底边 1440 量起预留 **123pt**；窗口底边落在 1317，像素级测量与玻璃顶边差 **0.0pt**。

**外部改尺寸的纠正**（第三方最大化、Option＋拖动）：这两类操作不经过事件 tap，只在接管成功后才装 `AXObserver` 观测该窗口的 `kAXWindowMovedNotification` / `kAXWindowResizedNotification`，几何稳定后若有窗口压住预留带就把它收进可用区：

- 只纠正**已被接管过**的窗口，不触碰用户自由摆放的其它窗口。
- 纠正时保持左右位置与顶边，必要时同时收高度——第三方最大化会把窗口设成整屏高，只上移会把它顶出屏幕（实测 `target=(-0.0, -93.0, 2560.0, 1410)`，`fits=false`）。
- 观测回调有 0.25s 合并窗口，动画进行中（`activeTargets` 非空）不打断。

实测：整屏高的窗口被子最大化后自动收回 `(0, 30, 2560, 1287)`；窗口落在程序坞上（底边 1300 > 可用区底边）不再压住。
